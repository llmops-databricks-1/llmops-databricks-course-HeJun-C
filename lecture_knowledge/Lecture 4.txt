MLflow for GenAI
MLflow for GenAI can be thought of as a distinct layer on top of the MLflow concepts we’ve seen so far. While familiar building blocks still apply, such as experiment tracking for logging runs and registering models, the application of these features shifts significantly in the context of generative AI.
In GenAI workflows, we still log and register models, but we rely on the pyfunc flavor with a different abstraction. Instead of extending PythonModel, GenAI applications typically use classes such as ResponsesAgent, which are designed to represent agents rather than traditional predictive models.
Evaluation is also fundamentally different. Rather than focusing on standard ML metrics, GenAI evaluation centers on behavioral qualities and agent decisions. To support this, MLflow introduces traces to provide fine-grained observability into everything that happens inside an agent, including tool calls, intermediate steps, and execution flow in real time.
In the following sections, we’ll explore MLflow’s GenAI flavors and the fundamentals of MLflow tracing. From there, we’ll define a custom agent with tracing enabled and progressively build toward evaluation, logging, and registering the agent.
MLflow flavors


MLflow provides specialized flavors for agentic frameworks, including DSPy, LangChain, and LlamaIndex. These libraries simplify the orchestration of AI agents by providing high-level abstractions for components like tool use, memory, and LLM calling.

MLflow tracing
MLflow Tracing gives you visibility into what your LLM application is actually doing under the hood. It’s an OpenTelemetry-compatible observability layer that records execution traces for every request. By capturing inputs, outputs, and metadata at each intermediate step, including model calls, tool invocations, and control-flow decisions, it transforms the "black box" of an agent into a transparent process.
With tracing enabled, you’re no longer flying blind. Instead of receiving an incorrect final answer and guessing what went wrong, you can see the exact path the agent took to reach that response. This makes it much easier to debug failures, troubleshoot unexpected behavior, and assess performance as your application inevitably changes.
Let’s examine the specific components that make up an MLflow trace.
Anatomy of a trace
At a high level, a trace is conceptually similar to an MLflow run. Both belong to an MLflow experiment. The difference is that traditional experiments track model training cycles, whereas GenAI experiments use traces to capture live or simulated agent executions.
Each trace consists of two main parts: Trace Info and Trace Data:


Trace Info contains high-level metadata about an execution. This includes the experiment ID, trace status (for example, success or failure), and the total execution latency. It also supports tags, which add contextual information such as the user, session ID, or developer-defined key-value pairs. These tags are particularly useful for searching, filtering, and organizing traces during analysis, monitoring, and debugging.
Trace Data stores the actual execution payload. It contains the instrumented Span objects that capture the step-by-step behavior of your application from input to output. Spans record critical operations such as LLM invocations, tool calls, and intermediate processing steps, providing a detailed, end-to-end view of how a GenAI application executes in practice.
MLflow’s Span object is designed to be fully compatible with the OpenTelemetry Span specification. It is implemented as a dataclass and closely mirrors the OpenTelemetry Span model, while adding convenience accessors and helper methods tailored specifically for GenAI workloads. Each span records essential attributes such as inputs and outputs, start and end times, execution status, span ID, trace ID, and an optional parent ID for hierarchical traces.
MLflow supports a rich set of span types that represent common operations within GenAI applications, including:
* LLM: Language model inference.
* TOOL: Execution of external tools, functions, or APIs.
* RETRIEVER: Retrieval of relevant context, for example from a Vector Search index.
* MEMORY: Reading from or writing to conversational memory.
* EMBEDDING: Generating vector embeddings from text or other inputs.
* RERANKER: Re-ranking retrieved results based on relevance.
As with traditional ML experiment tracking, MLflow can automatically log traces. However, autologging is not always sufficient if you want to attach custom metadata and domain-specific context. To gain full control, we must use the MLflow tracing APIs.
MLflow Tracing APIs
The simplest way to trace a function is by using the @mlflow.trace() decorator. When applied, it creates a span for the duration of the decorated function and automatically captures the function’s inputs and outputs. For example, the following code produces a span named my_func that records the input arguments x and y, along with the function’s return value.
import mlflow


mlflow.set_experiment('/Shared/tracing-demo')


@mlflow.trace
def my_func(x, y):
   return x + y


The same can be achieved with the mlflow.start_span() function, which manually defines the span and its scope:


def my_func(x, y):
   return x + y


with mlflow.start_span("my_func") as span:
   x = 1
   y = 2
   span.set_inputs({"x": x, "y": y})
   result = my_function(x, y)
   span.set_outputs({"output": result})


It’s also possible to add additional context to a trace even when using the @mlflow.trace() decorator. For example, we may want to attach a session ID and request ID to the trace, and later pass the same information to the agent endpoint so the two can be linked. This can be done using the mlflow.update_current_trace() function. The example below shows how to add a session ID, git_sha, request ID, and tags related to the model serving endpoint:


import random
from datetime import datetime


timestamp = datetime.now().strftime("%Y%m%d-%H%M%S")
session_id = f"s-{timestamp}-{random.randint(100000, 999999)}"
request_id = f"req-{timestamp}-{random.randint(100000, 999999)}"


git_sha = "abcd"


@mlflow.trace
def my_func(x, y):
   mlflow.update_current_trace(
   metadata={
       "mlflow.trace.session": session_id,
   },
   tags={"model_serving_endpoint_name": "arxiv-agent-endpoint",
         "model_version": 1,
         "git_sha": git_sha},
   client_request_id=request_id
)
   return x + y


Generated traces can be searched using a workflow similar to MLflow experiment run searches. Traces are searchable by nearly any field. For example, the code below demonstrates how to search for traces using the git_sha tag:


mlflow.search_traces(filter_string=f"tags.git_sha = '{git_sha}'")

Defining a custom agent
The ArxivAgent class inherits from the mlflow.pyfunc.ResponsesAgent. This base class requires us to implement prediction logic that produces ResponsesAgentResponse objects (or streams of response events).
Initialization and Async Handling
To initialize the class, we provide the Databricks Model Serving endpoint name, a system prompt, and the MCP tools defined earlier. During this stage, we use the WorkspaceClient to retrieve an OpenAI-compatible client for model serving.
This setup ensures that the agent has everything it needs to orchestrate LLM calls and tool invocations. Notice that we set the MLflow experiment here, and also use the create_mcp_tools function we defined earlier. Here we use the nest_asyncio package, which allows async code to run in environments where an event loop is already running. Python does not allow nested event loops, and calling asyncio.run() would raise an error. The nest_asyncio.apply() function patches the existing loop, enabling async functions like create_mcp_tools to execute from synchronous code:

from mlflow.pyfunc import ResponsesAgent
from mlflow.types.responses import (

   ResponsesAgentResponse,

   output_to_responses_items_stream,
   to_chat_completions_input,
)


from arxiv_curator.config import ProjectConfig
from arxiv_curator.mcp import create_mcp_tools
from arxiv_curator.memory import LakebaseMemory

class ArxivAgent(ResponsesAgent):
   def __init__(
       self,
       llm_endpoint: str,
       system_prompt: str,
       catalog: str,
       schema: str,
       genie_space_id: str | None = None,
       lakebase_project_id: str | None = None,
   ):
       """Initializes the Arxiv Agent."""
       nest_asyncio.apply()


       self.system_prompt = system_prompt
       self.llm_endpoint = llm_endpoint
       self.workspace_client = WorkspaceClient()
       self.model_serving_client = (
           self.workspace_client.serving_endpoints.get_open_ai_client()
       )


       # Initialize Lakebase memory if configured
       self.memory: LakebaseMemory | None = None
       if lakebase_project_id:
           self.memory = LakebaseMemory(
               project_id=lakebase_project_id,
           )


       # Create tools from config
       host = self.workspace_client.config.host
       tools = asyncio.run(create_mcp_tools(
           w=self.workspace_client,
           url_list=[
               f"{host}/api/2.0/mcp/vector-search/{catalog}/{schema}",

           ],
       ))
       self._tools_dict = {tool.name: tool for tool in tools}
If lakebase project ID is provided, LakebaseMemory class is initialized so that the agent can retrieve and store messages using session ID.
Core Agent Logic
The get_tool_specs method returns the tool specifications in the format expected by OpenAI-style chat completions. Each ToolInfo object exposes a spec that describes the tool’s name, parameters, and purpose. These specifications are passed to the LLM so that it can decide when and how to call a tool during generation:
  def get_tool_specs(self) -> list[dict]:
       """Returns tool specifications in the format OpenAI expects."""
       return [tool_info.spec for tool_info in self._tools_dict.values()]
This method executes a tool by name with the arguments provided by the model. It looks up the corresponding ToolInfo and calls its execution function. While you may notice tracing annotations here, we intentionally skip their explanation for now and revisit them in the next section. Conceptually, this method forms the bridge between the LLM’s structured tool calls and your application logic. You can notice we use the @mlflow.trace decorator to trace the tool execution:
   @mlflow.trace(span_type=SpanType.TOOL)
   def execute_tool(self, tool_name: str, args: dict) -> Any:
       """Executes the specified tool with the given arguments."""
       return self._tools_dict[tool_name].exec_fn(**args)


The call_llm method invokes the LLM endpoint and streams its output, yielding partial response chunks as they arrive. It uses exponential backoff to retry requests in case of rate-limiting errors. The method converts internal messages into the chat-completions format expected by the OpenAI-compatible API, attaches tool specifications, and enables streaming.
For observability, we manually create an MLflow span using mlflow.start_span instead of relying on @mlflow.trace. This allows us to capture additional information, such as the request ID from the response headers, and explicitly set span outputs after the stream completes. The request ID is included so you can trace which MLflow span corresponds to a specific LLM call, making debugging and monitoring much easier.
   @backoff.on_exception(backoff.expo, openai.RateLimitError)
   def call_llm(
       self,
       messages: list[dict[str, Any]],
   ) -> Generator[dict[str, Any], None, None]:
       with warnings.catch_warnings():
           warnings.filterwarnings(
               "ignore", message="PydanticSerializationUnexpectedValue"
           )
           stream = self.model_serving_client.chat.completions.create(
               model=self.llm_endpoint,
               messages=to_chat_completions_input(messages),
               tools=self.get_tool_specs(),
               stream=True,
           )
           with mlflow.start_span(name="call_llm", span_type=SpanType.LLM) as span:
               span.set_inputs({"messages": messages})
               last_chunk: dict[str, Any] = {}
               for chunk in stream:
                   chunk_dict = chunk.to_dict()
                   last_chunk = chunk_dict
                   yield chunk_dict
               llm_request_id = stream.response.headers.get("x-request-id")
               outputs: dict[str, Any] = {
                   "model": last_chunk.get("model"),
                   "usage": last_chunk.get("usage"),
               }
               if llm_request_id:
                   outputs["llm_request_id"] = llm_request_id
               span.set_outputs(outputs)
When the model decides to call a tool, the handle_tool_call method handles the execution flow. The tool arguments are parsed from JSON and the corresponding tool gets executed. The tool output is wrapped into a function-call output item and gets appended to the running message history. The ResponsesAgentStreamEvent is returned completing the tool call:
   def handle_tool_call(
       self, tool_call: dict[str, Any], messages: list[dict[str, Any]]
   ) -> ResponsesAgentStreamEvent:
       """
       Execute tool calls, add them to the running message history,
       and return a ResponsesStreamEvent w/ tool output
       """
       args = json.loads(tool_call["arguments"])
       result = str(self.execute_tool(tool_name=tool_call["name"], args=args))


       tool_call_output = self.create_function_call_output_item(
           tool_call["call_id"], result
       )
       messages.append(tool_call_output)
       return ResponsesAgentStreamEvent(
           type="response.output_item.done", item=tool_call_output
       )
The ArxivAgent class provides dedicated methods for loading and saving messages to memory. While this may seem redundant, it ensures each operation is properly traced via the mlflow.trace decorator. By isolating memory access in these methods, both loading and saving are captured as separate trace spans, improving observability and making debugging easier:
   @mlflow.trace(span_type=SpanType.RETRIEVER, name="memory_load")
   def load_memory(self, session_id: str) -> list[dict[str, Any]]:
       """Load previous messages from Lakebase memory."""
       if self.memory:
           return self.memory.load_messages(session_id)
       return []


   @mlflow.trace(span_type=SpanType.CHAIN, name="memory_save")
   def save_memory(
       self, session_id: str, messages: list[dict[str, Any]]
   ) -> None:
       """Save new messages to Lakebase memory."""
       self.memory.save_messages(session_id, messages)
The call_and_run_tools method implements the core agent loop. It builds the message history from the system prompt, optional previous messages (loaded from memory), and the current request, enabling stateful interactions. It then runs _run_tool_loop, which alternates between executing tool calls and invoking the LLM until a final response is produced or a maximum number of steps is reached.
The method is traced with @mlflow.trace and enriched via mlflow.update_current_trace(), adding tags such as git_sha, model_version, and model_serving_endpoint_name. These environment-based tags ensure every run is traceable and make it clear whether the code was executed locally or behind a serving endpoint.
Finally, if memory is enabled, the method saves both the input and generated outputs, allowing future calls to continue the conversation seamlessly.
   @mlflow.trace(span_type=SpanType.CHAIN)
   def call_and_run_tools(
       self,
       request_input: list[dict[str, Any]],
       previous_messages: list[dict[str, Any]] | None = None,
       request_id: str | None = None,
       session_id: str | None = None,
   ) -> list[ResponsesAgentStreamEvent]:
       messages: list[dict[str, Any]] = [
           {"role": "system", "content": self.system_prompt},
       ]
       if previous_messages:
           messages.extend(previous_messages)
       messages.extend(request_input)


       mlflow.update_current_trace(
           tags={
               "git_sha": os.getenv("GIT_SHA", "local"),
               "model_serving_endpoint_name": os.getenv(
                   "MODEL_SERVING_ENDPOINT_NAME", "local"),
               "model_version": os.getenv("MODEL_VERSION", "local"),
           },
           metadata=(
               {"mlflow.trace.session": session_id} if session_id else {}),
           client_request_id=request_id,
       )


       events = self._run_tool_loop(messages)


       if session_id and self.memory and request_input:
           self.save_memory(
               session_id,
               request_input + self._extract_output_items(events),
           )
       return events
Prediction and Streaming
The predict method implements the non-streaming interface required by ResponsesAgent. It simply calls predict_stream, collects the emitted events, and returns the final outputs as a ResponsesAgentResponse, making it suitable for synchronous or batch use cases.
The predict_stream method serves as the main entry point for execution. It extracts the session_id and request_id from the request, loads any previous messages from memory, and converts the incoming inputs into the internal message format.
The predict_stream method delegates all core execution logic to call_and_run_tools, which we discussed earlier. It then yields the resulting events as they are produced:
   def predict(self, request: ResponsesAgentRequest) -> ResponsesAgentResponse:
       events = list(self.predict_stream(request))
       return ResponsesAgentResponse(
           output=self._extract_output_items(events),
           custom_outputs=request.custom_inputs,
       )


   @mlflow.trace(span_type=SpanType.AGENT)
   def predict_stream(
       self, request: ResponsesAgentRequest
   ) -> Generator[ResponsesAgentStreamEvent, None, None]:
       custom = request.custom_inputs or {}
       session_id = custom.get("session_id")
       request_id = custom.get("request_id")


       previous_messages = (
           self.load_memory(session_id)
           if session_id and self.memory else []
       )


       request_input = [i.model_dump() for i in request.input]
       events = self.call_and_run_tools(
           request_input=request_input,
           previous_messages=previous_messages,
           request_id=request_id,
           session_id=session_id,
       )
       yield from events

LLM system evaluation
Before we deep dive into the code, let’s talk about what evaluating an LLM system means. Simply put, evaluation is the systematic process measuring a system’s quality. In traditional machine learning systems, we rely on well-established evaluation metrics to make this judgement, such as accuracy or F1 score for classification, and RMSE or R² for regression. LLM systems, however, are much harder to evaluate, which is why evals, a term commonly used by practitioners to refer to LLM evaluations, are often treated as an afterthought.
During the LLM system development phase, teams can get pretty far with manual testing and gut feeling. However, once the system reaches production and is used by real users, building without evals quickly becomes unsustainable. After you receive complaints and make changes to the system, there is no reliable way to know whether other behaviors have not silently regressed.
Just as we wouldn't skip evaluation in a standard ML workflow, we shouldn't skip it here. Evals are most valuable when implemented early for several reasons::
* Explicit Behavior: They force you to define exactly what "good behavior" looks like for your agent.
* Measurable Impact: They allow you to measure how changes to orchestration logic, prompts, or the underlying model affect performance.
* Hyperparameter Optimization: In many ways, choosing a prompt or a temperature setting is like tuning hyperparameters in classic ML; evals provide the data needed to make those choices.
How to evaluate LLM systems
If you’re starting with evals early, the best approach is a simple, iterative loop. Experts Aishwarya Naresh Reganti and Kiriti Badam, in their materials on AI Evals, suggest this workflow:
1. Create examples: Start small. 10–20 high-quality examples are better than 100 mediocre ones.
2. Run test cases: Process them through your current agent.
3. Evaluate with the business: Did the output meet expectations?
4. Identify error patterns: Explain exactly why an output failed..
5. Decide on key metrics: Determine what you are actually measuring..
6. Iterate and expand: Refine your prompts or tools and repeat.
They mention that the resulting reference dataset doesn't need to be large right away: 10-20 high-quality examples beat 100 mediocre ones.
Anthropic's Demystifying evals for AI agents adds a few useful principles:
* Product requirements naturally translate into test cases: if a requirement states that “the agent must cite its sources,” this can be turned into a test that verifies whether responses include references to the retrieved documents.
* The "Expert Agreement" Rule: A good test case is one where two domain experts would independently reach the same pass/fail verdict. If they disagree, the example is too noisy.
* Test Negative Behaviors: Don't forget to test both cases where a behavior should occur and where it shouldn't. Imbalanced datasets are just as problematic in agent evaluation as they are in traditional ML.

As a next step, you should identify metrics. A metric represents a behavior or quality you want to track over time. Examples include tool usage correctness (for example, did the agent attempt to retrieve data from history), tone appropriateness, number of tool calls, latency, and cost. For systems that produce structured output, common metrics include structured output correctness or simple quantitative measures such as output length or character count.
Once metrics are defined, you choose graders to measure them. A grader (also called a scorer) is the mechanism used to evaluate a metric. In practice, agent evaluations typically rely on three types of graders:
* Code-based graders are deterministic checks implemented directly in code. Examples include string or regex matching, character or token counts, output structure validation (for example, using Pydantic, as shown earlier), tool call verification, latency measurement, and cost tracking. Code-based graders are fast, inexpensive, objective, and reproducible, making them ideal to introduce early and run continuously. Their main limitation is a lack of nuance: they are poorly suited for evaluating subjective or context-dependent behaviors.
* Model-based graders, often referred to as LLM judges, use a language model to assess qualities that are difficult to capture with code alone, such as adherence to guidelines, correctness of reasoning, tone, or contextual appropriateness. These graders are more flexible and can handle open-ended outputs, but they are more expensive and non-deterministic. To be reliable, they typically require calibration against human judgment.
* Human graders are unavoidable if you want an LLM system that truly meets business expectations. While slow and expensive, human evaluation, ideally performed by subject matter experts, serves as the gold standard. Human graders are essential for defining evaluation criteria, calibrating model-based graders, and reviewing edge cases. In production, they are often used for spot checks to ensure the system continues to behave as intended as user behavior and real-world conditions evolve.
It’s important to keep in mind that this is still a relatively young field. While terminology and naming conventions may vary and differ across tools and platforms, the underlying principles remain consistent. Each framework introduces its own vocabulary for similar concepts. With that context in mind, let’s take a closer look at the MLflow GenAI evaluation framework.
MLflow GenAI evaluation framework
Scorers serve as the core components of the MLflow GenAI evaluation framework. To help you get started, MLflow provides several predefined model-based scorers designed to assess different aspects of model or agent behavior.
At a minimum, every evaluation requires two things: inputs (what was provided to the system) and outputs (what the system produced). In addition, you must also specify the evaluation model that will act as the judge.
For some scorers, this information is sufficient: metrics like  RelevanceToQuery, Completeness, Fluency, and Safety can evaluate a response using only the inputs and outputs, without requiring any additional annotations.
Other scorers rely on user-provided evaluation criteria. For example, Correctness and Equivalence require explicit annotations, such as reference answers, expected facts, or task-specific expectations.
Finally, some scorers operate on agent behavior rather than just text output. Tool-calling and retrieval-related scorers require traces so they can inspect tool usage, parameters, and execution order. In addition, certain scorers that measure conversation guidelines or role adherence are session-based, meaning they evaluate the entire conversation or interaction sequence instead of individual input-output pairs.

	UserFrustration
	Is the user frustrated? Was the frustration resolved?
	No | Yes | Yes
	Predefined scorers in MLflow evaluate model behavior using instructions built directly into the library. They are useful for getting started quickly and for generating early evaluation signals, but on their own they are rarely sufficient for rigorous or production-grade evaluation.
To support more tailored evaluation needs, MLflow allows you to define custom scorers. The simplest of these is the Guidelines scorer, which lets you specify general, natural language rules that apply across tasks without requiring per-example expectations. Because guidelines are evaluated as pass/fail conditions, this scorer provides a fast and accessible way to customize evaluation behavior.
For more nuanced and flexible evaluation, MLflow offers template-based LLM scorers. These scorers enable richer evaluation logic by allowing the judge to reason over additional context, such as expectations, conversation history, or execution traces:


While more powerful, the differences between guidelines-based and template-based LLM scorers are not always obvious at first glance. To make these distinctions concrete, we’ll compare the Guidelines scorer with a template-based LLM scorer created using the make_judge function, starting with a simple example:
import mlflow
from mlflow.genai.scorers import Guidelines


# Example using Guidelines for escalation handling
mlflow.set_experiment("/Shared/guidelines-example")
escalation_guidelines = Guidelines(
   name="escalation_handling",
   guidelines=[
       "When a user indicates previous attempts failed, the response must "
       "acknowledge their efforts and either escalate or offer a new approach"
   ],
   model="databricks:/databricks-gpt-oss-120b"
)


data = [
   {
       "inputs": {"message": "Tried everything you suggested"},
       "outputs": "Have you tried restarting?",
   },
   {
       "inputs": {"message": "Tried everything you suggested"},
       "outputs": (
           "I understand you've already tried the previous suggestions "
           "without success. Let me escalate this to our senior support "
           "team who can look into this more deeply. In the meantime, "
           "could you share any error logs you've encountered?"
       ),
   },
]


mlflow.genai.evaluate(data=data, scorers=[escalation_guidelines])
This evaluation session created traces showing that the first example failed the guideline, and the second has passed it:
The Guidelines scorer produces binary outcomes (pass/fail). When you need more expressive feedback, such as a 1–5 rating, a continuous score, or structured diagnostic output, you should use a template-based LLM scorer. While this is just one example of when an LLM scorer is the better choice, it represents a common and practical scenario.
In the code snippet below, we create a judge that produces an escalation quality score (from 1 to 5) instead of a binary output. Notice that the make_judge function takes an instruction argument that contains template variables. Template-based LLM scorers support {{ inputs }}, {{ outputs }}, and {{ expectations }} template variables.
import mlflow
from mlflow.genai.judges import make_judge


# Example using make_judge for escalation quality evaluation (1-5 scale)
mlflow.set_experiment("/Shared/make-judge-example")
escalation_judge = make_judge(
   name="escalation_quality",
   instructions=(
       "Evaluate how well the response in {{ outputs }} handles the user's "
       "message in {{ inputs }} when they indicate previous attempts failed. "
       "Score from 1 to 5:\n"
       "1 - Ignores context, repeats already-tried suggestions\n"
       "2 - Acknowledges frustration but offers no new solutions\n"
       "3 - Offers a new approach but lacks empathy or clarity\n"
       "4 - Acknowledges efforts and offers a reasonable new approach\n"
       "5 - Empathetic, escalates appropriately or provides creative solution"
   ),
   model="databricks:/databricks-gpt-oss-120b",
   feedback_value_type=int,
)


mlflow.genai.evaluate(data=data, scorers=[escalation_judge])
This evaluation session creates traces showing scores 5 and 1 for the respective examples we provided:


One of the key benefits of using a template-based LLM scorer is the ability to better align automated evaluation with human judgment. You can add human evaluations directly through the MLflow UI and then combine those annotations with trace data and LLM-based judge evaluations to align the scorer.
In this example, we use the SIMBA (Stochastic Introspective Mini-Batch Ascent) optimizer from the DSPy library. It enables an LLM to analyze its own performance and derive improvement rules by sampling mini-batches, identifying challenging examples with high output variability, and either generating self-reflective rules or incorporating successful examples as demonstrations. Custom optimizers are also supported.
To effectively align the judge, it is recommended to have at least 10 traces available for optimization (Check out Databricks documentation for more details):
experiment_id = mlflow.search_experiments(
   filter_string="name='/Shared/make-judge-example'")[0].experiment_id


from mlflow.genai.judges.optimizers import SIMBAAlignmentOptimizer


# Retrieve traces with both judge and human assessments
traces_for_alignment = mlflow.search_traces(
   experiment_ids=[experiment_id],
   return_type="list"
)


# Filter for traces with both judge and human feedback
valid_traces = []
for trace in traces_for_alignment:
   feedbacks = trace.search_assessments(name="escalation_quality")
   has_judge = any(f.source.source_type == "LLM_JUDGE" for f in feedbacks)
   has_human = any(f.source.source_type == "HUMAN" for f in feedbacks)
   if has_judge and has_human:
       valid_traces.append(trace)


optimizer = SIMBAAlignmentOptimizer(
   model="databricks:/databricks-gpt-oss-120b"
)


aligned_judge = escalation_judge.align(optimizer, valid_traces)

   model="databricks:/databricks-gpt-oss-120b",


The key difference between an LLM-as-a-Judge and an Agent-as-a-Judge is that the latter has access to tools for inspecting traces stored in the MLflow backend. This allows it to retrieve high-level trace metadata, inspect individual spans, and search for patterns across spans using regular expressions.
Next to complex evaluation mechanisms, MLflow also supports code-based scorers, which allow you to implement custom evaluation logic directly in Python. These are best suited for deterministic checks such as structural validation, tool usage verification, latency or cost thresholds, and other objective criteria that are difficult or unnecessary to express in natural language.
Beyond evaluation, scorers also provide the objective metrics needed for prompt optimization. MLflow supports several optimization techniques, including MIPROv2 (Multiprompt Instruction Proposal Optimizer, Version 2) from the DSPy library.
MIPROv2 jointly refines task instructions and few-shot examples by bootstrapping candidate examples, proposing alternative instructions that reflect different task strategies, and selecting the best combination using Bayesian optimization. The optimizer can be used to tune both instructions and few-shot examples together, or to optimize instructions alone in a zero-shot setting.
Prompt optimization is conceptually similar to hyperparameter tuning in traditional machine learning: it is an iterative process that should be revisited periodically as your system, prompts, and data evolve.

We are intentionally keeping these examples straightforward; the goal here isn't to build the "perfect" agent, but to demonstrate the specific tools you need to operate an agent effectively. These evaluation results will be logged directly to your MLflow experiment for easy tracking and comparison.

Notice that we pass the env_pack argument with the value "databricks_model_serving". This indicates that we will use Databricks serverless optimized deployments, which significantly simplifies handling of custom dependencies.
Although the agent defined in the arxiv_agent.py script imports the custom arxiv_curator package, we do not log this package explicitly. The serverless environment packing mechanism handles dependency resolution automatically. For this to work correctly, both the model logging and registration steps must run in the same serverless environment.
Simplifying custom packaging is not the primary benefit of this approach. The main advantage is significantly faster agent deployment and autoscaling. Keep in mind that model registration takes slightly longer than usual.
Another important constraint to keep in mind is model size: Databricks serverless optimized deployments support a maximum model size of 1 GB, compared to 4 GB when environment packaging is not used.
