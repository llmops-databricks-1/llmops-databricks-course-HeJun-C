Serverless compute
For the course, we will be using serverless compute. While classic compute is still the best choice for ML projects, serverless compute is a great (even preferred) option for developing AI agents. Serverless compute can be used both for development purposes and running a Databricks job.
Unlike the all-purpose or job compute, we cannot choose the runtime for serverless compute. Instead, we can curate an environment for dependencies. While the concept of an environment and a runtime are similar, environments are much more lightweight.
Serverless environments
In our project, we use Python 3.12, which means we also need to have an environment that supports that Python version. In the course, we use CPU environment version 4, which comes with the following configurations:
* Operating System: Ubuntu 24.04.2 LTS
* Python: 3.12.3
* Databricks Connect: 17
* Scala: 2.13.16
* JDK: 17
Similar to runtimes, serverless environments come with pre-installed libraries. However, the library versions differ slightly between serverless environment 4 and runtime 17.3 LTS - something to watch for if your workflows switch between serverless and classic compute, as subtle version mismatches can cause unexpected behavior. We recommend installing your own versions of the libraries you need to ensure consistency across environments.
Similar to the runtimes, environments have support cycles of 3 years. End-of-support for environment 4 is in August 2028. You can check out the release notes for the full overview.
Cost tracking
While the costs of classic compute clusters can be tracked using tags, usage policies are used for serverless compute. Serverless usage policies consist of tags that are applied to any serverless compute activity incurred by users assigned to the policy. These tags are recorded in billing logs, enabling you to attribute serverless usage to specific budgets.
Usage policies can be created programmatically or through the UI, and permissions can be assigned to individual users or user groups. Important to notice that if a usage policy ID is not specified when using serverless resources, the first available policy (in alphabetical order) assigned to the user will be automatically applied (see figures below).

Secondly, all the package dependencies are pinned to very specific versions. While this may seem beneficial at first glance, it is not considered best practice for packages intended to be reused across multiple projects, as strict version pinning can easily lead to dependency conflicts.
For reusable packages, it is generally recommended to define a supported range of Python versions and dependency versions instead. In this case, however, the Python package is not designed for reuse, it simply serves as a convenient way to define and manage project-level dependencies.
When installing the package, there is no need to manually specify all dependency versions listed in the pyproject.toml file. These dependencies are included in the package metadata and will be installed automatically as part of the package installation process.
Optional dependencies are also defined in the pyproject.toml file and can be installed when needed, for example, for development purposes. Note that they will not be installed automatically when the package itself is added as a dependency as they are not included in package metadata.

Databricks development tools
There are four main local developer tools Databricks provides: Databricks CLI, Databricks Asset Bundles (or DABs), Databricks connect, and Databricks VS Code extension.
Databricks Command-Line Interface (CLI)
Databricks CLI is a command line interface that allows you to interact with the Databricks platform. It is a very powerful tool with a large range of commands that cover similar functionality as Databricks Terraform modules and APIs.
Databricks CLI should be used to authenticate towards Databricks from your local machine. So we need to start with installing it. Databricks provides a comprehensive documentation on how to do it on different OS.
Databricks CLI provides multiple authentication options. I do not recommend using personal access tokens (from a security perspective, this is not the best option). Instead, use user-to-machine authentication.
For the workspace-level commands, use the following command to authenticate:
databricks auth login --host <workspace-url>
It creates an authentication profile in the .databrickscfg file that contains the profile name and configurations for the profile. It is a good practice to use a user-understandable profile name, so that you can pass -p option when authenticating.


[llmops-course]
host  = https://dbc-1234a567-b8c9.cloud.databricks.com/
auth_type = databricks-cli


The profiles are used to authenticate with Databricks when using developer tools.
Databricks Asset Bundles
You may have noticed that the repository contains the databricks.yml file. This is the Databricks Asset Bundle configuration file, which must be located in the root of the bundle project folder.


At its core, Databricks Asset Bundles (DABs) enable you to manage Databricks projects through an infrastructure-as-code (IaC) approach. Using the databricks.yml file, you can define the artifacts and resources your project requires.


The minimal asset bundle configuration only contains the bundle name and the target:


bundle:
 name: my_bundle


targets:
 dev:
   host: <your_host>
   default: true


It’s worth mentioning the artifacts section is where you can specify which packages need to be built as part of the bundle deployment.

* It can run any build command, provided the dependency is installed (for example, uv build).
* For the whl type, you can set the dynamic_version parameter. If set to true, a dynamic version with a timestamp is created. This is crucial for jobs that use an interactive cluster, as it ensures the cluster uses the latest code changes. This isn't necessary for job clusters or serverless clusters, as they handle this behavior automatically.


artifacts:
 <some-unique-artifact-identifier>:
   build: string
   files:
     - source: string
   path: string
   type: string
   dynamic_version: boolean


This is what the bundle and artifacts sections of our databricks.yml file look like:


bundle:
 name: course-code-hub


artifacts:
 default:
   type: whl
   build: uv build
   path: .


For now, only the dev target is relevant. It is set as the default, which means it will be used whenever no target is specified when running databricks bundle CLI commands (which we’ll cover next).


targets:
 dev:
   default: true
   mode: development
   workspace:
     host: <your host>
     root_path: /Workspace/Users/${workspace.current_user.userName}/
                .bundle/${bundle.target}/${bundle.name}


It is crucial that the host defined in the target matches the Databricks profile you use to log in to Databricks. If you’ve forked the repository and cloned it to your local machine, make sure to update the host value in the databricks.yml file. Without this change, you won’t be able to run the code examples covered in the following sections.


The development mode specified for the target enables the following behaviour:
* It adds [dev ${workspace.current_user.short_name}] prefix to all resource names and tags each job with a dev Databricks tag.
* It allows you to override job clusters (which is not allowed in production mode).
* It pauses all schedules and triggers
* It enables concurrent runs on all deployed jobs and disables the deployment lock for faster iteration.
* The bundle's root path must be under the user's home directory.


There are 4 main Databricks CLI commands related to DABs:
* databricks bundle validate: Checks if your databricks.yml file is configured correctly.
* databricks bundle deploy: Deploys the resources defined in your databricks.yml file.
* databricks bundle run <job resource name>: Executes the specified job.
* databricks bundle destroy: Removes all the assets that were created by the bundle.


After the databricks bundle deploy command is executed, all the project files and built artifacts are uploaded to the root_path location specified under target. Here we’ll find:
* The artifacts folder, which holds the Python wheel files built for the project.
* The files folder, containing all your project's source files.
* The state folder, which stores the Terraform state of the bundle.


It’s important to pay attention to authentication when using DABs, specifically the evaluation order:
1. For any command run from the bundle working directory  - the values of fields within a project’s bundle setting files.
2. The values of environment variables (DATABRICKS_HOST and DATABRICKS_TOKEN).
3. Configuration profile field values within the .databrickscfg file.
If you happen to have an environment variable set up, it may mess up with authentication.

Let’s explore how to make notebooks available in the Databricks workspace and execute them there instead.
The Databricks VS Code extension allows you to sync the entire project to the workspace. After clicking Sync in the Remote Folder tab, the extension runs the databricks sync <folder> /Users/<user_name>/<folder> --watch command in the background. As a result, any local changes are automatically reflected in the workspace without requiring manual synchronization.
This approach can also be used to make a wheel file for your project available in the workspace. Simply run the uv build command, and the generated wheel will be synced along with the rest of the files (unless the wheel location is added to the .gitignore file).
It is important to note that the databricks sync command provides one-way synchronization. Changes made directly in the Databricks workspace are not reflected locally, and any subsequent sync will overwrite workspace code.
Alternatively, you can make the code accessible in the workspace using the Git Folder functionality. After creating a Git Folder, you can authenticate by linking your Git account to Databricks or by using a personal access token from GitHub or another supported version control provider. Git Folders enable bidirectional synchronization, allowing changes made in notebooks to be pushed back to Git (although this may become inconvenient when dealing with merge conflicts). In addition, managing project dependencies through Git Folders can be challenging.
Finally, you can use the databricks bundle deploy command (make sure to run it from the mlops folder that contains the databricks.yml file) to make all project files available in the workspace together with the built artifact, which is the main advantage of this approach over syncing. However, this method also provides one-way synchronization. Note that using the sync command together with bundle deploy may corrupt the bundle state.

Foundation models on Databricks
Working with foundation models on Databricks gives you flexibility: you can use ready-to-use hosted models, deploy models with provisioned throughput, or connect to external providers like OpenAI or Anthropic. In this section, we'll explore each option, discuss supported model types, and show you how to query them.
Hosting Options
Working with foundation models on Databricks gives you significant flexibility. The platform hosts a variety of ready-to-use foundation model APIs, including models like Meta Llama 4, Open AI GPT-5, and Gemini 3 Pro. Beyond these hosted models, you can deploy open-source models through provisioned throughput serving endpoints, or connect to external providers like Azure OpenAI, AWS Bedrock, and Anthropic.
Regardless of which option you choose, all models use Mosaic AI Model Serving, which follows the OpenAI API specification. It supports three endpoint types:
* llm/v1/chat (corresponding to the OpenAI Chat Completions API);
* llm/v1/embeddings (corresponding to the OpenAI Embeddings API);
* llm/v1/completions (following the legacy OpenAI Completions API).
This unified interface lets you query foundation models the same way, regardless of the provider or where the model is hosted. This consistency makes it much easier to experiment with different models, perform evaluations, or enable fallback strategies. You can even use an OpenAI client to interact with foundation models on Databricks. Note that at the time of writing, the responses API is only supported for Databricks-hosted OpenAI closed-sourced foundation models.
Here is an example of how we can interact with the databricks-gpt-oss-120b model:
from databricks.sdk import WorkspaceClient
from openai import OpenAI


w = WorkspaceClient()
host = w.config.host
token = w.tokens.create(lifetime_seconds=1200).token_value


client = OpenAI(
   api_key=token,
   base_url=f"{host}/serving-endpoints"
)


response = client.chat.completions.create(
   model="databricks-gpt-oss-120b",
   messages=[
       {"role": "user",
        "content": "What is MLOps?"}
   ]
)
Another benefit of using foundation models on Databricks is the AI Gateway. Gateway can be applied to any Mosaic AI Model Serving endpoint, including foundation model APIs. You can also enable AI Guardrails to ensure personally identifiable information (PII) data is deleted or masked and harmful content is blocked, for both model input and output.

Foundation model APIs can also be used in batch mode using ai_query (see the Databricks documentation on AI functions). Some Databricks-hosted models are optimized for batch processing, but ai_query works for any endpoint deployed through Mosaic AI model serving.
As mentioned earlier, Databricks offers three hosting options for foundation models, let’s discuss them in detail.
Databricks-hosted (Pay-per-Token)
These models are ideal for experimentation and exploration as they require no additional configuration or upfront infrastructure commitment. Model availability in your workspace depends on your cloud provider and region (see AWS and Azure documentation for details). However, they are subject to workspace-level rate limits in input/output tokens and queries per hour. The most restrictive rate limit applies at any given time; if reached, you will receive a 429 error until the window resets.
Provisioned Throughput
Recommended for production, these endpoints provide performance guarantees. You can deploy models behind provisioned throughput endpoints directly from the system.ai schema. You can also bring your own model (perhaps one you've fine-tuned) from sources like Hugging Face. For the latter approach, you'll need to log the model using MLflow (using the transformers flavor) and register it in Unity Catalog. It’s important to note that provisioned throughput works only for selected foundation model families and for specific runtime configurations (size and context window) that Databricks has tuned and supports. You can find supported models in this documentation. If you choose to bring your own model and its metadata falls outside supported ranges, the provisioned throughput endpoint creation will fail (source).
Measuring Capacity: Tokens per Second
For some models, provisioned throughput is expressed in tokens per second (input and output tokens combined), rather than requests per second. Since LLM requests vary widely in token lengths, requests per second is no longer a reliable measure of capacity. For example, if a request requires 2048 input tokens and 256 output tokens (2304 tokens total), a provisioned throughput of 2304 tokens per second allows the endpoint to process one such request per second. If you increase this to 4608 tokens per second, the endpoint can process two such requests per second, with each request still taking roughly one second to complete.
Autoscaling and Performance
Limits for provisioned throughput endpoints can be configured much higher than those for Databricks-hosted foundation models, and autoscaling adjusts capacity dynamically based on application demand.
For example, consider the meta_llama_v3_1_8b_instruct model:
* Its minimum band size is 9,500 tokens per second, which corresponds to four provisioned concurrency units.
* If the system detects a demand of 15,000 tokens per second while operating at four units, it will scale up to eight units.
* This increases the available throughput to approximately 19,000 tokens per second to meet the higher load.
Optimizing LLM inference performance is not an easy task, and GPU autoscaling is slower than CPU autoscaling for regular model serving endpoints.  Databricks recommends conducting benchmarking to choose the correct range of tokens per second. It is possible to scale the endpoint to 0 to avoid unnecessary costs, but it is not recommended for production environments.
For other models, provisioned throughput is expressed in model units, which is an abstraction layer on top of tokens per second.  For the Llama 4 Maverick model, for example, 50 model units means approximately 3250 tokens per second.
External models
External models are hosted outside of Databricks, which means you may need to configure firewall rules to access them (AWS). Various providers are supported, and you can also use custom providers as long as their APIs are OpenAI-compatible.
Even though you could access external models directly from the agent logic (given that the secrets are configured and the networking is resolved), creating a serving endpoint that accesses an external model is a good idea because of the benefits mentioned above, specifically around governance.
The custom provider option can also be used when you need to use functionality, such as those offered by OpenAI, that are not yet covered by out-of-the-box solutions. For instance, while Databricks’ existing OpenAI external model serving options currently support text and image inputs with text-only outputs, the “Custom Provider” solution enables support for image as output (encoded as base64) use cases through Databricks. Types of foundation models
Foundation models on Databricks are categorized into four functional types to help you select the most effective tool for your specific application:
* General purpose: These models are fine-tuned on large datasets of human dialogue, which enables them to generate contextually relevant responses in multi-turn conversations. They are ideal for use cases such as customer support, virtual assistants, interactive tutoring systems.
* Embedding: These  models transform complex data, such as text, images, or audio, into embeddings that capture the essential features and relationships within the data. They are recommended for applications that require semantic understanding, similarity comparison, and efficient retrieval or clustering of complex data.
* Vision: Designed to analyze visual data, these models are used for object recognition and image classification. Note that while they accept image inputs, standard configurations typically produce text outputs unless using a Custom Provider setup.
* Reasoning: These models excel at breaking down complex tasks, and explaining their decision-making process. They are best suited for  content creation, summarization, and agent orchestration.
