Context engineering & RAG
In the early days of AI engineering, it was all about prompt engineering. While well-crafted system prompts remain important, modern agent systems demand much more. Today, we need strategies to manage the entire context state, which includes external data, available tools, conversation history, and intermediate reasoning steps.
Consider an agent running in a loop. Each turn generates new information (tool outputs, retrieved documents, user clarifications) that may be relevant for subsequent reasoning. But context windows are finite. The challenge isn't just getting information to the model; it's about shaping more behavior and curating what goes in, when, and how - this is what modern context engineering is about.
In the course, we'll explore three core aspects of context engineering:
1. From raw data to agent context: How agents access and retrieve information beyond their training data.
2. MCP servers on Databricks: A standardized protocol for exposing tools and data sources to agents.
3. Agent memory using Lakebase: Maintaining state and conversation history across interactions.
This lecture covers the first part. Parts 2 and 3 (MCP servers, function calling, agent memory) will be covered in lecture 3.

Reference Architecture: The arXiv Curator
To make these concepts concrete, we'll build a system that generates LinkedIn posts about recent ArXiv papers on AI, written in a consistent style. To achieve this, our system will:
* Download and process full paper PDFs: Extracting the complete text, not just metadata. This gives us access to results, examples, and insights buried deep in the paper.
* Chunk and embed the content: Storing vector representations in a Databricks Vector Search index for semantic retrieval.
* Track paper metadata in a Delta table: Recording which papers we've processed, when, and their key attributes. In lecture 3, we'll create a Genie space on top of this table for natural language querying.
* Expose these resources via MCP (lecture 3): Both the Vector Search index and Genie space are available as managed Databricks MCP servers. This means our agent can access them through a standardized tool interface, which we'll explore in detail in the next section.
Now, we could take a simpler approach: the ArXiv API already provides titles and abstracts, which might be sufficient for basic posts. But we want to create higher-quality, more insightful content that’s hard to create based on the abstracts.
We intentionally made the architecture more sophisticated than strictly necessary for our toy example. These patterns (PDF ingestion, vector retrieval, structured metadata, tool protocols) appear in nearly every production LLM system. Building them here, even for a simple use case, teaches transferable skills you'll apply to more complex scenarios.
For a real production system though, I encourage you to think the other way around: go simple first, and more complex only if necessary. I recommend checking out the blog by Anthropic on building effective agents to understand different complexity levels when it comes to AI systems.
From raw data to agent context
Data Ingestion
We utilize the ArXiv Python package to search for the latest papers in the AI category from the ArXiv database. We will then download the papers, store them in a volume, and save all the metadata in the arxiv_papers table within the configured catalog and schema. The packaged version of the code can be found in the src/arxiv_curator folder under the data_processor module.
Here we use incremental processing based on timestamps. If the arxiv_papers table exists, the system queries the timestamp of the most recently processed paper and searches ArXiv for all papers published between that timestamp and the current execution time. This ensures that only new papers are downloaded and processed, avoiding redundant work.
Note: Databricks Free Edition has network restrictions that block outbound API calls to certain external services. If you use the Free Edition, you wouldn’t be able to call the ArXiv API in a Databricks notebook. Consider developing locally instead, and then upload files to Unity Catalog Volumes using Databricks CLI.

After the papers are stored in the volume and all the metadata is stored in a delta table, we're going to tackle PDF processing - one of those problems that looks deceptively simple until you actually try to do it at scale.
PDF parsing
PDFs are everywhere in enterprise environments, and they're consistently one of the hardest data sources to work with reliably. That's because PDFs weren't designed for data extraction. They were designed to ensure the document looks exactly the same, does not matter where you view it or print it.
PDFs are built for visual presentation but lack metadata to process content reliably. They may look organized on screen but are unstructured behind the scenes. It makes them incredibly frustrating when you need to extract structured data for processing, search, or feeding into your AI systems.
You may find several options when it comes to PDF processing (including scanned documents): open-source projects like docling, or solutions provided by cloud vendors like AWS Textract and Azure Document Intelligence. Modern LLMs with vision capabilities can now process PDFs directly. Models like GPT-5, Claude Sonnet 4.5, and Gemini 3 Pro can see the document layout, understand context, handle both native text and scanned images, and extract structured data in a single pass.
Databricks also provides an ai_parse_document function that significantly simplifies the PDF processing pipeline and handles all of this complexity behind the scenes, providing high accuracy for a competitive price. Let's see how it works in practice.
Note: The ai_parsed_docs function is not supported while executing code locally via VS Code.

Chunking
Effective chunking is critical because it directly impacts the quality of information retrieved in response to user queries. To understand the impact of chunking, let’s inspect one of the documents. We are interested specifically in chunks with regular text content. The length of chunks varies, for example: 9% of chunks have <100 characters, 5% chunks have >1000 characters, 70% chunks have 100-500 characters.


The chunking has been done intelligently and mostly preserves the structure of the document making it a good enough starting point for indexing and usage later for retrieval. Overall, chunking matters more than most people realize as it directly impacts what gets retrieved when users ask questions.
Chunking Strategies
The simplest approach is splitting documents into equal-length chunks based on some unit, such as characters, words, sentences, or paragraphs. This performs reasonably well for many use cases but has a fundamental problem: it doesn't respect the structure of your content. For instance, a 2,048-character chunk might cut off mid-sentence, mid-paragraph, or right in the middle of a critical explanation. Context gets lost at the boundaries. One of the ways to solve it is using overlapping. If your chunks are 2,048 characters, you might use 200 characters of overlap. This ensures that information near chunk boundaries appears in at least one complete chunk. The downside: you're duplicating some content and increasing your index size.
For arXiv papers, a recursive document splitting can be applied based on the maximum token size. Start by splitting at section boundaries (Abstract, Introduction, Methods, Results). If a section is too long, the logic further divides it by subsections, such as Data Collection, Model Architecture, or Training Procedure, and finally into individual paragraphs. This hierarchical approach preserves the document's logical structure and reduces the risk of arbitrarily breaking related content, ensuring that retrieved information remains contextually complete.
Embedding Window Considerations
When determining chunk size, you must consider the embedding window of your chosen  model. For instance, the Databricks GTE model has an embedding window of 8192 tokens, whereas the Databricks BGE Large model has an embedding window of 512 tokens. It’s important to distinguish between character counts and tokens. Tokens can represent words, sub-words, or punctuation depending on the model's tokenizer. For instance, the phrase "MLOps is awesome" contains 16 characters but is processed as only 3 tokens: [“MLOps”, “is”, “awesome”].
Processing chunks
To make the data usable for vector search, we need to create another table where each chunk is stored in a separate row. Let’s create a user-defined function to extract the chunks. Here, we are only extracting chunks of type text:
import re
import json
from pyspark.sql.types import (
   ArrayType,
   StringType,
   StructField,
   StructType,
)
from pyspark.sql.functions import (
   col,
   concat_ws,
   explode,
   udf,
)




def extract_chunks(parsed_content_json: str) -> list[tuple[str, str]]:
   parsed_dict = json.loads(parsed_content_json)
   chunks = []


   for element in parsed_dict.get("document", {}).get("elements", []):
       if element.get("type") == "text":
           chunk_id = element.get("id", "")
           content = element.get("content", "")
           chunks.append((chunk_id, content))
   return chunks


chunk_schema = ArrayType(
   StructType(
       [
           StructField("chunk_id", StringType(), True),
           StructField("content", StringType(), True),
       ]
   )
)
extract_chunks_udf = udf(extract_chunks, chunk_schema)
We also want to extract the paper id from the path, and clean chunks (remove whitespaces, fix hyphenation, collapse new lines into spaces):
def extract_paper_id(path):
   return path.replace(".pdf", "").split("/")[-1]


extract_paper_id_udf = udf(extract_paper_id, StringType())




def clean_chunk(text: str) -> str:
   t = re.sub(r"(\w)-\s*\n\s*(\w)", r"\1\2", t)
   t = re.sub(r"\s*\n\s*", " ", t)
   t = re.sub(r"\s+", " ", t)


   return t.strip()


clean_chunk_udf = udf(clean_chunk, StringType())
Finally, we can create the table arxiv_chunks, and enable change data feed so that we can use the table to create and incrementally update the vector search index. Notice that we are joining some fields from the metadata table so that we can perform reranking and filtering later:
metadata_df = spark.table(metadata_table).select(
   col("paper_id"),
   col("title"),
   col("summary"),
   concat_ws(", ", col("authors")).alias("authors"),
   (col("published") / 100000000).cast("int").alias("year"),
   ((col("published") % 100000000) / 1000000).cast("int").alias("month"),
   ((col("published") % 1000000) / 10000).cast("int").alias("day"),
)


chunks_df = (
   df.withColumn("paper_id", extract_paper_id_udf(col("path")))
   .withColumn("chunks", extract_chunks_udf(col("parsed_content")))
   .withColumn("chunk", explode(col("chunks")))
   .select(
       col("paper_id"),
       col("chunk.chunk_id").alias("chunk_id"),
       clean_chunk_udf(col("chunk.content")).alias("text"),
       concat_ws(
           "_", col("paper_id"), col("chunk.chunk_id")
       ).alias("id"),
   )
   .join(metadata_df, "paper_id", "left")
)


chunks_table = f"{catalog}.{schema}.arxiv_chunks"
chunks_df.write.mode("append").saveAsTable(chunks_table)


spark.sql(
   f"""ALTER TABLE {chunks_table}
   SET TBLPROPERTIES (delta.enableChangeDataFeed = true)
   """
)
Vector search index
At this point in the pipeline, we have arXiv papers stored as PDFs in volumes, their metadata in Delta tables, parsed content extracted via ai_parse_document, and chunks stored in a Delta table. Databricks provides Mosaic AI Vector Search functionality that allows to make this content searchable.
Vector search is fundamentally different from traditional search. Instead of matching keywords, it works with embeddings - mathematical representations of semantic content. Text with similar meanings produces similar vectors, even if the exact words are different.
If we take scientific papers, researchers don't always use the same terminology. One paper might discuss "convolutional neural networks" while another talks about "CNNs" or "ConvNets." Vector search handles this naturally because it understands that these concepts are semantically related.
Creating the Endpoint and Index
To get started, we must first create a vector search endpoint. Mosaic AI Vector Search provides standard and storage-optimized endpoint configurations. Standard endpoints have a capacity of 320 million vectors at dimension 768 while storage-optimized ones can accommodate over one billion vectors of that dimension and provide 10-20x faster indexing. Queries on storage-optimized endpoints have a slightly increased latency, and there is some difference in supported operations between different endpoint types. Consult Databricks documentation for details.
We can create a vector search endpoint programmatically using the VectorSearchClient. Notice that we pass here the usage policy ID which will be used later for cost allocation:
from databricks.vector_search.client import VectorSearchClient


from arxiv_curator.config import ProjectConfig


cfg = ProjectConfig.from_yaml("../project_config.yml")
catalog= cfg.catalog
schema = cfg.schema


vsc = VectorSearchClient()
vector_search_endpoint_name = "vector-search-arxiv-endpoint"
endpoint_exists = any(
   item.name == vector_search_endpoint_name for item in vsc.list_endpoints()
)
if not endpoint_exists:
   vsc.create_endpoint_and_wait(
       name=vector_search_endpoint_name,
       endpoint_type="STANDARD",
       usage_policy_id=cfg.usage_policy_id)


Once the endpoint is active, we can proceed with creating a vector search index. We use the create_delta_sync_index function from the VectorSearchClient. This function requires the following arguments:
* Columns to sync: Columns to transfer from the source table. If undefined, all columns are synced.
* Vector search endpoint name: The name of the endpoint where the index is served.
* Source table name: The Delta table containing the input data.
* Index name: The full name for the new index.
* Primary key: The unique identifier (in our case, the id from the chunks table).
* Embedding source column: The column containing the text to be embedded.
* Embedding model endpoint name: The foundation model API used to generate embeddings (we use the Databricks-hosted databricks-gte-large-en model).
* Pipeline type: The type of Lakeflow Spark Declarative Pipeline used for synchronization. We choose “TRIGGERED”.
vs_index_fullname = f"{catalog_name}.{schema_name}.arxiv_index"


embedding_model_endpoint = "databricks-gte-large-en"


index = vsc.create_delta_sync_index(
   endpoint_name=vector_search_endpoint_name,
   source_table_name=f"{catalog}.{schema}.arxiv_chunks",
   index_name=vs_index_fullname,
   pipeline_type="TRIGGERED",
   primary_key="id",
   embedding_source_column="text",
   embedding_model_endpoint_name=embedding_model_endpoint,
)
When the new data is available in the source table, we will have to run the sync command:
index = vsc.get_index(index_name=vs_index_fullname)
index.sync()
Overall, use TRIGGERED mode unless you need fresh data within a few minutes. For lower latency requirements, CONTINUOUS mode ensures updates arrive within seconds.

It’s important to note that the create_delta_sync_index command does not just create the Vector Search Index, but also computes the embeddings. This allows us to query the index using natural language. The same model used to create the embeddings  is automatically applied to your query to retrieve the most relevant documents.
It is also possible to bring your own embeddings. In this case, the source Delta table should contain pre-computed embeddings instead of text. While this offers more control, it also means you are responsible for generating the corresponding embeddings within your LLM application at query time. Querying and Retrieval Quality
Mosaic AI Vector Search supports natural language queries. For the similarity_search function, we need to provide the following arguments:
* columns: The fields to return in the results.
* query text or query vector: Query as a text or as embedding if “bring your own embedding” option is chosen.
* filters: SQL-like filters to restrict results by metadata (e.g., specific years or authors). Filter operators like “=”, “>=”, “<=”, “IN”, “LIKE”, “NOT”, “OR” are supported. Syntax varies per endpoint type. Consult documentation on querying vector search for more details.
* number of results: The number of chunks to retrieve.
* score threshold: Defines a minimum similarity score for results. Any document with a score below this threshold is excluded, even if it ranks within the top K results.
* query type (ANN” or “HYBRID”). Mosaic AI Vector Search uses the Hierarchical Navigable Small World algorithm for its approximate nearest neighbor (ANN) searches and the L2 distance distance metric to measure embedding vector similarity. The hybrid keyword-similarity option matches exact words in the query while also using a vector-based similarity search to capture the semantic relationships and context of the query. This method is particularly useful in RAG applications where source data has unique keywords that are not well suited to pure similarity search.
* operational arguments: Configuration for debugging levels, retry limits, suppression of warnings (via disable_notice), and backoff factors between retry attempts.
* reranker and columns to rerank. Reranking is a technique that improves retrieval quality by evaluating the retrieved documents to identify the ones that are semantically most relevant. Databricks has developed a reranker that you can use right away, where you can also specify columns containing additional context relevant for reranking, such as paper summary and title.
This is how the similarity_search function can be used:
from databricks.vector_search.reranker import DatabricksReranker


results = index.similarity_search(
   query_text="Chunking strategies for document processing",
   columns=["text", "id"],
   filters={"year": "2026"},
   num_results=5,
   query_type = "hybrid",
   reranker=DatabricksReranker(columns_to_rerank=["text", "title", "summary"])
   )
Optimizing Search Quality
To understand the impact of configuration changes, it is important to establish evaluation metrics and a test dataset.
For a test dataset, you can use existing labeled query-answer pairs, generate synthetic test cases from your documents, or use LLM judges to assess quality without labels. Even a small synthetic dataset of 50 queries is enough to tell you whether hybrid search improves quality or whether reranking helps.
When it comes to evaluation metrics, pick based on what failure looks like for your application. Once you have metrics aligned with your use case, you can systematically test configurations and know which changes actually improve retrieval quality.
Key metrics include:
* Recall@k: Measures how many relevant items were successfully retrieved. Critical for legal or financial use cases..
* Precision@k: Measures what percentage of retrieved items are actually relevant. Critical for technical support where only the best result matters.
*  F1@k balances: Balances both precision and recall..
Databricks guide on vector search retrieval quality outlines 8 main steps AI engineers should consider:
1. Enable hybrid search: One-line code change may improve recall by catching both semantic and keyword matches, and improve precision for queries with specific terms.
2. Use metadata filtering: Reduces the search space, improves recall within the filtered subset, and precision by eliminating irrelevant results.
3. Add reranking: Databricks built-in reranker is a great solution, but is not suitable for high QPS applications (>5 QPS without additional scaling) or applications with low latency requirements. In those scenarios, it might be a good idea to build a custom reranker that utilizes a model serving endpoint.
4. Improve data preparation: Refine document parsing and chunking strategies.
5. Query expansion: Generate multiple query variations to improve recall.
6. Prompt optimization: Use automatic prompt optimization techniques to improve prompts used for data preparation or query rewriting.
7. Adaptive retrieval strategies: Build agents that can reformulate queries or decide if retrieval is necessary.
8. Embedding model finetuning: A final option if standard models do not provide satisfactory results, particularly for non-English languages.
